# Product

Read when deciding what a feature should do, how concepts relate or what the product says. Interaction guidance is in [ui.md](ui.md); file formats and protocols belong in [contracts/](contracts/).

## Purpose

LabShelf connects reading, developing ideas and writing in scientific research. Its audience is researchers and students who read papers with equations, work with code and usually write in LaTeX or Typst: mathematicians, engineers, data scientists, programmers and researchers using statistics in fields such as biology.

Their work is spread across reference managers, manuscript editors, computational notebooks and conversations with advisors or collaborators. Each tool requires its own organization and sharing, while the relationships between the work are left to the researcher. LabShelf should reduce that fragmentation and the dependence on multiple paid tools.

Judge a feature by how it helps someone understand a paper, develop or reproduce a result, discuss the work or carry it into a manuscript. Preserve the connections between these activities as the work develops.

## General

- Basic work should be easy to discover and complete without reading documentation. Advanced tools can expose deeper controls without making the basic path harder.
- Reading, notes, calculations, discussion and writing belong to the same research workflow. Make their connections useful: return to a source passage, consult a note while writing or keep a discussion with the material it concerns.
- Equations, code and results are research content. Support examining, editing and reusing them alongside prose and references.
- Library, Projects and Spaces describe different responsibilities. Use these concepts consistently across apps, while adapting the available tools to the host.

## Library

The Library is the researcher's reusable collection of papers, metadata, PDFs, annotations and paper notes. It remains useful across topics and manuscripts. Folders organize the collection; a paper can be recorded before its PDF is available.

Use paper and folder consistently. Reading states are Unread, Reading and Done.

## Projects

A Project is a writing project: a LaTeX or Typst manuscript and its supporting files, notes, references and work toward a PDF. It draws on the Library. Coauthors can collaborate on a writing project.

Moving material into a manuscript should preserve a useful route back to its source. A note or calculation can remain exploratory while the manuscript presents the result.

In VS Code a `.tex` or `.typ` file of a project opens in the LabShelf editor by default. Its title bar has a Reopen in Text Editor button that reopens the file in VS Code's text editor, and the text editor offers Reopen with LabShelf Editor to come back; a user who wants the text editor as the default maps the files to `default` in `workbench.editorAssociations`. Jumps to a line (reverse SyncTeX, the outline, project search, links between project files) reveal the line in the file's LabShelf editor, opening one when none is open, rather than opening a second tab in the text editor. The LabShelf editor is a card like the PDF preview with the project's own tools: build problems as squiggles, an "N notes" line over each line citing a paper with notes (as the native editor's code lens), insert from a note, citation completion from the library, labels, and comments. The title actions, build and preview act on it when it is focused. It edits the same document as a native editor on the file, so both show every edit. In a shared project it shows peers' edits and cursors, publishes the user's selection and undoes only the user's own edits; closing it withdraws the selection it published. LaTeX Workshop, language servers, Copilot, Vim, VS Code's native completion, hover and definition providers, `.bib` files and the terminal app stay with the native editor.

The source editor of a LaTeX or Typst file, in the browser and in VS Code, has a mode switch in its toolbar. In Editing, edits apply directly. In Reviewing, every edit stays in the file, so the PDF compiles the proposal, but is tracked as a suggestion: insertions are highlighted, deletions are shown struck through, each with its author and time. Anyone who can edit the file accepts or rejects one suggestion, a replacement or all of them from the editor, in local and shared projects. The mode is remembered per user and per project, and a new project starts in Editing.

A writing project holds talks and posters as decks: HTML files marked as a talk or poster, each with a `theme.css` and its assets beside it ([decks](contracts/decks.md)). New Presentation and New Poster in the project menu create one in `talks/<name>/` or `posters/<name>/`; LabShelf recognises one anywhere in the project by its content, and the Files tree marks it Talk or Poster. An external Claude writes decks through `labshelf mcp`, which hands out the editability rules, reads the project's outline, sections, figures and references, and refuses any write outside the deck folders or with a rule error. The user edits a deck in the deck editor in VS Code and the browser: move, resize and edit text, reorder, add, duplicate and delete slides, change the theme and the size, set a block's text style and position in a properties panel, add rectangles, ellipses and lines, or edit the source; every other byte of the file stays as it was. A block can link to a figure, equation, table or citation of the paper; it says Out of date when the source changes and updates on request. A talk is presented with an audience view and a presenter view with notes, a timer and the next slide. A poster is previewed at real size with a calibrated ruler, and text too small to read at print size is listed. A deck exports as one offline HTML file or as a PDF of its page size through a Chromium (in the terminal, `labshelf deck export`); without one the HTML opens to print. Share Deck as Link shares a deck by link as a folder is shared; the link opens in a viewer that presents it, Insert QR Code puts the link on a slide, and revoking it in Manage Shared Links makes it unreadable.

A talk or poster written in LaTeX or Typst (a beamer, tikzposter or similar class, a Typst slide or poster package, or a source marked `labshelf: talk|poster`, anywhere in the project) opens in a workspace in the LabShelf Editor and the browser's source tab. It has three modes. Visual shows the slides or blocks, the built page and the selected block's properties. Split shows the code beside the page, and the cursor and the page follow each other. Code is the editor as it is for any other file. In Visual the user clicks a block on the page, then edits its title, figure, width, caption, alignment or column, moves, duplicates or deletes it, and inserts text, figures, equations, tables and lists. Each change rewrites only that part of the source and rebuilds the PDF. A talk also gets New slide by layout, speaker notes edited in place and Present; a poster gets Real size. The Theme menu switches beamer and tikzposter themes and colours, or a Typst source's heading colour.

## Spaces

A Space provides context around a topic or research effort: papers, linked writing projects, notes, discussions, dates and a glossary. It is encouraged through its usefulness and is optional. Reading a paper or creating a project never requires creating a Space.

Library and Projects remain global. A paper or project can belong to several Spaces without a copy; removing its reference from a Space leaves the original in place. Space folders organize references independently of Library folders.

## Home

- Home is the start page that brings Library, Projects and Spaces together. It opens from the Home row at the top of the browser sidebar and from the Home button of the VS Code LabShelf view.
- **On your desk** is personal and fully manual: the user pins papers, projects, whole Spaces, or a note or topic of a Space, and adds personal tasks (a title, a short description, an optional date and an optional link to a paper, project or Space). It holds at most 8 cards in a strip that scrolls sideways. Checking a task removes it. The desk is stored in `home.json` and is never shared.
- **Needs you**, **Up next** and **Recent in your Spaces** fill themselves. Needs you lists overdue tasks and today's dates from every active Space, plus desk tasks that are due today or late. Up next lists the coming dates and dated desk tasks in order. Recent is a placeholder until Spaces record activity. Connecting a calendar and pinning a note or topic from Home are shown but still in development.
- Personal multi-step work is just an unshared Space; Home only gathers it.

## Math in notes

In a `.qmd` note, the LaTeX a researcher already writes is read by the note's Mathematica session, so the note computes and checks itself without leaving the sentence. It needs Mathematica, in VS Code and in the browser (through LabShelf Helper). Without it, or in a read-only view, a note shows the results it already holds and offers no action.

- **Inline results.** An inline math that ends in `=` gets its simplified result right after it when the researcher leaves it; ending in `\approx` gives the numeric value. An equation with derivatives (an ODE) offers Solve, which inserts its solution the same way. Nothing is computed without an action of the researcher. The result is stored in the note as a Pandoc span, `$expr =$ [$result$]{.labshelf-result engine=mathematica source=<hash>}`, so the file stays standard Quarto, renders anywhere without executing anything, and a reader without Mathematica sees the last result. The hash covers the expression and the Mathematica cells above it, because variables come from the note's session. When either changes, the result shows as out of date and offers Recompute; it is never recomputed on its own.
- **Step checks.** Each `=` of a derivation, in inline or display math, is checked in the background after the researcher edits it, like a spell-checker. A step is ✓ proved, ≈ agreeing at sampled points but not proved, ✗ differing with a counterexample, ⚠ true only under a condition, or ? unread. Checks run only for math edited in the current session, never when a note opens or in a read-only view, and are never written to the file. Sampling uses positive reals; integer and assumption domains are not read from the text, so a step true only on another domain can show ✗. Over-alarm is preferred to hiding an error.
- **Honest reading.** Every result and mark shows how the math was read by Mathematica and which rewrites were applied (for example `e^{x}` as the exponential, or `\frac{dy}{dx}` as a derivative of `y(x)`), because a silent misread is the main risk. Math that cannot be read safely is marked unread and nothing runs.
- **Scope.** Mathematica only; SymPy and other engines, warnings in ordinary cells and equations taken from the PDF are not part of this. The terminal app shows the result span as raw text, as it does for outputs.

## Notebook flow

A `.qmd` note with code cells (Python, Mathematica, R) behaves like a notebook while the file stays plain Quarto. Everything below is about the open view; none of it is written to the file except the results of cells.

- **Warnings.** A cell that returns a result and also warns shows the result with its warnings on a quiet line under it. Only a cell with no result, or one that raises an error, is an error. Warnings and the run time belong to the run just made: a reopened note shows the stored result and its `ran` time only.
- **Run time.** After a run the cell shows how long the computation took, not the wait in a queue.
- **Run many.** Run all, Run above, Run below, Run section and Restart and run all run the cells one at a time in note order, across the items of the note. The run stops at the first error, timeout, missing language or Stop; the cells after it say they were not run. In the reader the note is the open item; in a paper's notes editor, Spaces and a project note it is every item editor shown. Pending cells show Queued, the status shows "Running k of n" and one Stop cancels the current cell and drops the rest.
- **May be out of date.** When a cell is edited or rerun, the later cells of the same language that ran before it say they may be out of date and offer Run below. LabShelf knows order and time, not data flow, so it never says a cell is checked or current. It clears when the cell reruns.
- **Collapse and the Advanced switch.** A cell collapses to one summary line, a section collapses to its next heading, and Collapse all and Expand all do the whole note. A note reads clean by default: a cell shows its results, or one summary line when it has none, and its code opens on request, while a new or empty cell shows its code to be written. The Advanced switch turns the note into a workbench: every cell shows its code with its results under it, the line numbers stay with a bar over each block, the block being edited is marked and shows its source (Markdown with its LaTeX and Quarto syntax) while the caret is in it, and the note's tools show as buttons. Both are for editing. All of this is remembered per note on the device, never written to the file and never synced.
- **Organising a long note.** An outline lists headings, cells and figures in note order with problem badges; F8 and Shift-F8 jump to the next and previous problem; Alt-up and Alt-down move a cell or a section; a plus between blocks inserts a cell, equation, drawing, chart or text; a cell can be duplicated (without its output) or change language. Long text outputs show their first lines with Show all, and the current section's heading stays in view.
- **Scope.** A variables inspector, a slash menu, folding sections across items and a soft interrupt (Stop still ends the language's session) are not part of this.

## Charts in notes

A `.qmd` note holds charts: function plots and data charts made in a fullscreen chart editor and drawn live with Plotly, in the same host, with the same light and dark theme as the plots of cells. Chart is in the Insert menu and the plus between blocks, after Drawing, and opens a picker of 12 tiles: Function Plot, Function 3d Plot, Scatter, Line, Area, Contour, Heatmap, Pie, Bar, Surface 3d, Scatter 3d and Mesh 3d. A chart in a note opens in the editor on click or Enter, and the outline lists it. Cancel leaves the note as it was; Apply writes the chart and keeps the editor open; Ok writes it and closes.

- **Data charts.** A chart has one or more traces, each with a type, the columns it reads for X, Y and Z, and options such as transpose; Style panels set the title, colours, colourscale, legend, axis titles, ranges, ticks, grid and log axes. The data is a spreadsheet grid under the preview: cells edit, rows and columns add and delete, pasted spreadsheet or CSV text fills it, and Import data from CSV file reads a file.
- **Large data.** A small table is stored in the note. A table that would make the chart too large for the note is stored as a CSV file in `assets/` beside the note, named by the chart, and the note refers to it. The file stays when the chart is deleted. When the file is missing, or the host cannot read it, the chart shows its stored image under "Data file not found" and its data cannot be edited.
- **Charts of tables.** Hovering a table of a note (a Markdown table or a LaTeX table block) or of a LaTeX source, or putting the selection in it, shows a Chart button at its top right. Its menu offers the charts the table can make, the suggested one first (lines over a numeric first column, bars over names): lines, scatter, area, bars, stacked bars, pie, heatmap, surface 3D and scatter 3D; a LaTeX source offers only those pgfplots draws. The chart goes right after the table and follows it: every edit of the table redraws it, and one undo takes back both. The link is the table's label, its Quarto `{#tbl-…}` caption or its LaTeX `\label`; a table without one gets one. In the chart editor the table of such a chart is read-only and edited in the document. Typst files have no charts.
- **Function plots.** In 2D a plot holds expressions in x (`y = f(x)`, `x = f(y)`), inequality regions, parametric and polar curves and implicit curves `F(x, y) = 0`, each with a colour and a domain. Expressions are plain text, checked as the user types, and an invalid one shows its message and where it breaks. Named variables have a value and an optional slider that redraws the plot while it moves. In 3D a plot holds `z = f(x, y)` surfaces, parametric surfaces and 3D curves, each with a domain and number of steps, a colourscale and a preview the user rotates. The editor remembers the 3D camera and each variable's value, so reopening the chart, the note and the image all show what the user left on screen.
- **Image and PDF.** Ok and Apply store a PNG of the chart beside its definition, so HTML, Word and viewers without Plotly show the chart; if the image cannot be made the note says "No image for export yet". In PDF output through LaTeX, the charts pgfplots can draw (function plots except implicit curves and inequalities, line, scatter, area and bar charts, scatter 3d) come out as vector figures; the rest use the PNG. The document needs `\usepackage{pgfplots}` in its header; LabShelf does not edit the header, and without the package the PNG is used.
- **Scope.** A chart stays standard Quarto: a reader without LabShelf sees the image or the figure. The ideas still open are in [charts-ideas](ideas/charts-ideas.md).

## Supporting choices and scope

LabShelf is local-first. The user's own sync tool moves the library between devices; this is distinct from live collaboration. Without a folder, the browser stores the library internally and must explain that uninstalling the extension deletes that storage.

The browser extension, VS Code extension and terminal app offer different ways into the work. Keep shared concepts and behavior consistent and check the host's capabilities when designing a flow.

LabShelf is in active development. Screens with mock data and prototype interactions can express and help evaluate product direction before the underlying capability is integrated. Preserve that exploration while distinguishing it from working persistence, computation or collaboration. Check the relevant host before claiming support. [Ideas](ideas/) explore future work and can lag behind implementation; they are not feature specifications.
