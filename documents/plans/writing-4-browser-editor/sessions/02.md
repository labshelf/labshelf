## 2.1 — Web build

- **Goal:** add a `browser` entry and an esbuild target so the extension runs in a web extension host.
- **Decided:**
  - The extension is written once and runs in VS Code and in the browser editor page (D1). The web build contains only code outside `node/` folders, so everything Node-only (LaTeX build, `node:*` use, child processes, native file access) is absent or sits behind a port that has a web implementation.
  - LaTeX projects in the web build show "Compile on desktop" instead of building (D5). Typst compiles in the page, not in this package.
  - No code is copied from `packages/browser/`; the web build imports only `core` and third-party packages. The `browser` entry lives in this package's manifest (`package.json` `browser` field) next to `main`.
  - Contracts in `documents/contracts/` do not change.
- **Read only:** the extension manifest (`packages/vscode/package.json`), its esbuild script, the composition root under `packages/vscode/src/` (find with `grep -rl "activate" packages/vscode/src`), and every `node:` import under `packages/vscode/src/` (`grep -rn "from \"node:" packages/vscode/src`) to list what must be gated or ported.
- **Done when:**
  - the web bundle builds and loads in a web extension host (a minimal test page; the real page is session 3);
  - tests, written with the change, pin the behaviour of each gated feature: the web build offers "Compile on desktop" for a LaTeX project and does not reach a Node API;
  - `pnpm --filter @labshelf/vscode typecheck && pnpm --filter @labshelf/vscode test && pnpm --filter @labshelf/vscode build`, and the same typecheck and test for `core`.
- **Do not touch:** `packages/browser/`, `core` contracts, `documents/contracts/`.
