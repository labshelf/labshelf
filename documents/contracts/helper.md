# Contract: LabShelf Helper protocol

Read when you change a message between the browser extension and LabShelf Helper, a limit, the socket handshake, the helper's data folder or how it builds.

LabShelf Helper builds LaTeX and Typst projects for the browser extension. The extension, the standalone helper binary, the VS Code extension and the terminal app all ship separately, and the last two can serve this host too. Any version of the page meets any version of the helper, so the protocol version rises with every change to a message, a limit or the handshake.

## Transport

The page starts the helper through native messaging (`dev.labshelf.helper`) and sends `hello`. The helper answers `ready`, then `session` with a loopback port and a random token. The page opens a WebSocket to `127.0.0.1` and its first frame is `auth` with that token. The helper lives as long as the native port and exits when stdin closes.

The native port is the only channel the browser authenticates (the manifest names the allowed extension). The token carries that identity to the socket, because any local process or web page can reach a loopback port. So the helper refuses and logs the reason when:

- the socket's `Origin` differs from the origin `hello` sent, is not `chrome-extension://<id>` or `moz-extension://<uuid>`, or differs from the caller origin Chrome passes as first argument;
- the first frame is not a correct `auth` within a short time limit;
- a second socket presents the token. One token serves one socket; a reconnect goes through a new native port.

Native frames from the helper stay under the browser's host-message limit.

PLATFORM: Firefox upgrades `ws://` to `wss://` under `upgrade-insecure-requests`, so the Firefox manifest's `extension_pages` CSP must not carry that directive.

## Messages

Every message has `v`, an `id` of 1 to 64 characters chosen by the page, and a `type`. Replies and `progress` carry the request's `id`; only an `error` for a frame without a valid `id` has none. Unknown keys are dropped on read.

- `root` of `openProject`, and every later `path`, `main` and `editedFile`, resolve with the [bridge's confinement](bridge.md#paths) under the library root of the [shared configuration](library-format.md#shared-configuration). Escaping, also through a symlink, is refused with `path`. A `projectId` that was not opened is refused with `project-id`.
- Builds and edits never write into the library. The helper builds a copy with the unsaved text in place. `save` means the page wrote the file itself: the helper drops its unsaved text and rereads.
- An `edit` carries the whole text or non-overlapping `changes` in UTF-16 offsets of the previous version. Changes that do not apply answer `stale` and the page sends the whole text.
- `pages` carries only the pages that differ from the last `pages` on this socket for the project, all of them after `openProject`. A successful build sends `pages` even when nothing changed.
- `built` `{status, problems, pdfSha256?, pageMap?}` answers a `compile`. After a full LaTeX build that succeeded it may carry `pageMap`, the build's [page map](decks.md#page-map) (`{pages: ({file, line, kind} | null)[], blocks: {file, line, page, rect}[]}`, at most 5000 entries in each list); a malformed or oversized `pageMap` rejects the message like any other invalid field. The parser drops unknown keys, so the field needs no version bump: an older page ignores it.
- A `.typ` compile runs the bundled WASM Typst compiler with fonts and packages only from the helper's data folder.
- `installPython` installs the managed Python ([managed-tools.md](managed-tools.md#python)) and answers `progress` with phase `python`, then `ready`; a failure answers `error` with code `python-install-failed`.
- `runCell` `{code, cwd, timeoutMs, language, noteKey, params?, preview?}` runs one code cell and answers `cellResult` `{status, language, restarted?, latex?, text?, error?, controls?, plot?, warnings?, durationMs}` under the same `id`. `language` is `python`, `mathematica` or `r` ([qmd-items.md](qmd-items.md#cell-languages)); Python runs in the interpreter from `labshelf.cells.pythonPath`, else the first `python3` or `python` on PATH, else the managed Python; Mathematica in `wolframscript` and R in `Rscript`. `noteKey` is an opaque string the host derives from the note (`paper:<paper id>`, `space:<space id>:<note path>`, `project:<project id>:<note path>`); the helper keeps one driver process per `noteKey` and `language`, so cells of one note share variables. `status` is `ok`, `error`, `timeout`, `cancelled` or `missing` (the language has no executable). `durationMs` is the time from sending the request to the driver to its reply, without queue wait or start-up. `restarted: true` means a fresh process ran the cell after the previous one was killed, so earlier definitions are gone. `code` is at most 1 MiB (larger is refused with `limit`) and `timeoutMs` an integer from 1 to 600000. `cwd` is a scope, never a path: a project id or `paper:<paperId>`. A project id resolves to the folder of that project while it is open, `paper:<paperId>` to the temp folder; an unknown scope is refused with an `error` under the request `id` and nothing runs. A malformed scope is refused with `project-id`.
- `params` is an object of at most 8 cell parameters ([qmd-items.md](qmd-items.md#cell-parameters)), each name matching `^[A-Za-z][A-Za-z0-9_]*$` and each value a finite number, a string or a boolean; anything else is refused with `invalid-field` and nothing runs. The helper passes the values to the driver as data, never as code. `controls` comes back only when a Mathematica cell ends in `Manipulate`: a list of `{name, kind, min?, max?, step?, choices?, value}` with `kind` `slider`, `select` or `checkbox`. `preview` is a boolean marking a preview run whose result the page shows but never stores; drivers may skip work for it. `plot` is the labshelf-plot spec JSON ([qmd-items.md](qmd-items.md#outputs)); the socket's frame cap is its only size limit. `warnings` is the driver's warning lines of the run, sent only when there are any; the page keeps it only when it is an array of at most 21 strings of at most 500 characters and otherwise drops that field alone. The parser already drops unknown keys, so the field needs no version bump.
- `cancelCell` `{requestId}` aborts the run that `runCell` started under that `id`, which then answers `cellResult` with `cancelled`. It does not wait in the queue behind other messages, and for an id that is not running it answers nothing. Cancel and timeout kill that language's process for that note.
- `restartCell` `{noteKey, language}` kills that language's process for that note without running anything; the next `runCell` starts a fresh one. Like `cancelCell` it does not wait in the queue.
- `evalMath` `{noteKey, cwd, op, tex}` computes or checks one piece of TeX on the note's Mathematica session and answers `mathResult` `{result}` under the same `id`; `result` is the `MathResult` of the cell runner as is (`state` `value`, `proved`, `sampled`, `differs`, `conditional`, `unread` or `failed`, with `latex?`, `readAs?`, `rewrites`, `messages`, `counterexample?`, `condition?`, `restarted?`). `op` is `eval`, `numeric`, `solve` or `check`; `tex` is at most 8 KiB of UTF-8 (larger is refused with `limit`); `noteKey` and `cwd` follow `runCell`. It queues behind the earlier messages, and nothing cancels it once sent: the page that gives up drops the reply and sends no `cancelCell`. A failure in the runner answers `error` under the `id`.
- `ready` carries `python` (`missing` or `installed`) when the host reports it, on `hello` and after an install. A helper that omits it predates Python.
- `ready` carries `capabilities`, a list of feature names; every `ready` this helper sends lists `printPdf` and `ocr`. The page keeps the string entries (unknown names too), drops other entries and drops a value that is not a list. A `ready` without it announces nothing, and the page keeps the capabilities an earlier `ready` of the session announced.
- `printPdf` `{size}` (socket only, never the native port) carries the deck's exported HTML as the frame's binary payload in UTF-8, at most 15 MiB (`MAX_PRINT_HTML_BYTES`, under the 16 MiB socket message). `size` is the deck's `data-deck-size` string (`1920x1080px`, `841x1189mm`); the page size comes from the HTML's own `@page` rule and `size` only validates. The helper prints it with headless Chromium (the system one, else the managed one when installed; it never installs it) and answers `pdfPrinted` `{bytes}` with the PDF as the payload, or `printFailed` `{reason, message}` with `reason` `noChromium`, `limit` (HTML over the limit, or a PDF over the 16 MiB socket message) or `failed` (a size that is not a deck size, a Chromium failure, a cancelled run). The page sends it only when `ready.capabilities` lists `printPdf` and refuses a larger HTML itself before sending. It queues behind earlier messages.
- `cancelPrint` `{requestId}` (socket only) aborts the print that `printPdf` started under that `id`, which then answers `printFailed` `failed` with `Cancelled.`; the page has already stopped waiting. Like `cancelCell` it does not wait in the queue, and for an id that is not printing it answers nothing.
- `installPix2tex` installs the managed pix2tex ([managed-tools.md](managed-tools.md#pix2tex)) and answers `progress` with phase `python` and message `Installing pix2tex`, then `ready` with the usual fields and capabilities; a failure answers `error` with code `pix2tex-install-failed`.
- `ocr` `{bytes}` (socket only) carries one equation image as the frame's binary payload, a PNG of at most 4 MiB (`MAX_OCR_PNG_BYTES`); `bytes` is its length. The helper reads it with pix2tex ([managed-tools.md](managed-tools.md#pix2tex)) and answers `ocrResult` `{latex}`, or `ocrFailed` `{reason, message}` with `reason` `missing` (no pix2tex found), `limit` (PNG over the limit, checked before anything runs) or `failed` (the read failed, or the run was cancelled with `Cancelled.`). Exactly one reply answers each `ocr` id. The page sends it only when `ready.capabilities` lists `ocr`; the client resolves `unsupported` itself otherwise. It queues behind earlier messages.
- `cancelOcr` `{requestId}` (socket only) aborts the read that `ocr` started under that `id`, which then answers `ocrFailed` `failed` with `Cancelled.`; the page has already stopped waiting. Like `cancelPrint` it does not wait in the queue, sends no reply of its own, and for an id that is not running it is ignored.
- `texlive-rollover` means a managed TeX Live is a year behind the package repository. The page asks before reinstalling ([managed-tools.md](managed-tools.md#rollover)).
- `publishTemplate` follows [templates.md](templates.md#publish): it publishes saved files only, repeats every check on a snapshot before submitting and keeps no GitHub token on disk.

## Version

The protocol version is 11. The page compares `ready.protocol` with its own. A lower helper version asks to update the program that `host` names; a higher one asks to update LabShelf in the browser. When the helper refuses `hello` for `version`, its `error` carries the helper's `v` so the page can tell which side is older. It cannot know the host then, so it names LabShelf Helper, the VS Code extension and the terminal app. The page never shows the raw error. The standalone helper then runs its update check at once.

A new optional feature does not bump the protocol: the helper announces it in `ready.capabilities` (as `printPdf` and `ocr`), and the page treats a helper that does not list it as one that lacks the feature and asks to update LabShelf Helper only for that feature.

## Data folder

The data folder holds the build copies (`projects/<projectId>/src`, with latexmk output kept in `build/`), template publication snapshots (`publishing/`, deleted when done), Typst fonts and packages, biber's WASM tree named by its sha256, `pix2tex/` (`pix2tex_worker.py` and `pix2tex-requirements/`, which the standalone binary writes from its embedded copies at start-up so Python and pip can read them), `bin/` and `logs/`. The managed TeX and Python are not here: they are in the folder every app shares ([managed-tools.md](managed-tools.md)).

On macOS and Linux the folder and `logs/` are `0o700` and log files `0o600`. The standalone helper exits non-zero, naming the path, when its binary, the folder holding it (unless root owns it), its data folder or `bin/` is writable by group or others.

## Registration and updates

- `labshelf-helper --register` writes the manifests of this host and of the [bridge](bridge.md) for every supported browser; `--unregister` removes both. `--uninstall` also removes the bridge name and `bin/`, keeping projects and the shared managed tools (TeX and Python). It writes nothing outside the user's home. Precedence over the desktop apps' launchers is in [native-host.md](native-host.md#precedence).
- Only the standalone binary updates itself, rate-limited after `hello`, from `latest.json` of the latest GitHub release. It accepts an update only when the Ed25519 signature verifies against the built-in key and the download matches its `sha256`. The new binary runs from the next launch.

## Build safety

- TeX never runs with shell-escape: `-no-shell-escape`, `openout_any` and `openin_any` set to `p`, and latexmk with `-norc` so no `latexmkrc` runs. A project that needs shell-escape ends `needs-shell-escape`.
- On macOS and Linux the helper serves as latexmk's biber (`--biber --root <project>`). It runs biber's WASM build in-process when the `.bcf` version matches and every data source is local, else the TeX's own `biber`. It refuses a data source outside the project, the build folder and `TEXMFROOT`.
