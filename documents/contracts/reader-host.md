# Contract: PDF reader and its hosts

Read when you change the PDF reader or the code that hosts it.

The PDF reader is one UI that runs inside two hosts: the VS Code webview and a browser extension page. Hosts own persistence, clipboard, files, external links and settings. The reader owns everything on screen. They talk only through the typed message protocol in the reader's `protocol` module, which is the single source of truth for message shapes.

One host controller in core answers every message the reader sends. Each host implements the controller's ports (sidecar store, posting to the reader, preferences, the auto theme, clipboard, notices, external links, saving the Markdown export, logging, and optional hooks for sidecar changes and reading activity) and keeps only its own lifecycle: creating the view, forwarding theme and preference changes, and asking for a page.

## Startup

1. The host serves the HTML shell (shared by both hosts) with an inert JSON boot block, `ReaderBootParams`. The block carries the protocol version, asset URLs, paper id and title, theme preference and effective theme, reader preferences and `isMac`.
2. The host's entry calls `startReader({ boot, transport, perf, pdf? })`. The transport hides how messages travel: `postMessage` in VS Code, in-page calls in the browser. `pdf` lets a host supply the paper bytes and the worker. The browser starts workers from the extension URL, because Firefox refuses `blob:` workers.
3. The reader sends `ready-for-init`. The host answers `init` with the reading state, annotations, preferences and theme.
4. The reader sends `ready` with the page count once the document is laid out.

## Rules

- **Every message has one handler.** Adding a message means adding its handler to the shared host controller; a host changes only when the message needs a port it does not implement yet.
- **`citeInProject` asks the host to cite a paper in a writing project.** The message carries `paperId` and optionally `page` (a positive integer) and `quote` (at most 2,000 characters). The controller passes it to the host's optional `citeInProject` port; a host without the port shows the notice `Cite in project is not available here`.
- **Messages wait for `ready`.** The reader drops host messages other than `init` and `applyTheme` before the document is laid out. The controller holds the latest of each type and sends them on `ready`.
- **Every failure is logged and shown.** A handler that throws is logged with the paper and command and becomes a `Reader action failed` notice; a rejected annotation write becomes a `Failed to create|update|delete annotation` notice and the reader keeps its list.
- **The host validates untrusted input.** Messages from the reader go through `isWebviewMessage`, so a malformed message is rejected and never half-applied. External links go through `isSafeExternalUrl`, which allows only `http:`, `https:` and `mailto:`, so a crafted PDF cannot open `file:`, `command:` or `vscode:` URIs.
- **Preferences are validated once.** Both hosts pass stored preferences through the shared `normalizeReaderPrefs`. VS Code reads them from settings; the browser reads them from extension storage.
- **The sidecar format is shared.** The host persists annotations, theme and reading position through the shared `PaperDataStore` over a `SidecarPort`, which keeps the bytes identical everywhere ([library-format.md](library-format.md#sidecar-datajson)).
- **Highlights are drawn on their page.** A highlight the reader creates carries its selection's box in the page as `position` ([library-format.md](library-format.md#sidecar-datajson)); the reader draws every annotation with a `position` over its text on that page, and lists the ones without one in the Annotations tab only.
- **Reading position is saved only after restore.** The reader does not report a position until it has restored the stored one, so the initial page-1 layout never overwrites it.
- **`PROTOCOL_VERSION` changes whenever a message changes shape.**

## Preview

A host can show a build's output in the reader, e.g. a writing project's compiled PDF. It then implements the controller's preview ports and drives the reader through the controller:

- **Reload in place.** After a build replaces the PDF, the host asks for a reload. The reader re-reads the bytes and keeps the page, the offset on it and the zoom. A failed build leaves the file and the reader untouched. A reload may name another file; the reader then shows it, at the place it last showed that file in this panel, else its first page.
- **Build status.** The host reports `building`, `succeeded`, or `failed` with the error count, the time of the last successful build of the shown root (`builtAt`, milliseconds since the epoch) and whether a project source was saved or edited since then (`stale`). An edit sends a new status with `stale` set and the same state; only a successful build clears it. The reader never dims the PDF for a stale or failed build; it shows the state in its chrome, and clicking a failed state asks the host to open the first error.
- **Build roots.** After every build and every switch of the shown file, the host sends `previewRoots`: the project's main root, the focused root, the shown root, and for each root it has built its path relative to the project folder, whether its last build failed, whether a raw log exists, whether it links source and PDF positions, and its problems (severity, message, hint, file, line). Each message replaces the last. When a main build fails the host also sends `showLogs` with that root, so the reader opens its logs. A failed build never replaces the shown PDF.
- **Build logs.** The reader shows a root's logs over the page area: tabs by severity with counts, one entry per problem (an entry with a file sends `openProblem`), and Open raw log when the root has one. The build notice opens the logs of the root it reports. Back to PDF or Escape closes the logs and shows the PDF underneath, which is the last one that built.
- **Writing actions.** A preview reader asks the host to `recompile` the shown root, to open a problem's source (`openProblem`, by root and index in that root's problems), and to open a root's raw log (`openRawLog`). The host acts only on roots it reported; anything else is logged and ignored. A library reader never sends these. In a preview reader Ctrl/Cmd+S sends `recompile`, and F8 / Shift+F8 move to the next / previous problem on the PDF.
- **Page count.** When the project sets a page limit, `previewRoots` carries it as `pageLimit`; without a limit the field is absent and the reader shows no page chip. The reader counts the pages of the open PDF that hold the paper's body, shows "<pages> of <limit>" in the toolbar (ok below the limit, warn at it, err over it) and reports the count once per shown root and per document with `bodyPages` (`root` as in `previewRoots`, `contentPages`). A host without a `bodyPages` port ignores the message. A count that fails is logged in the reader and shows no chip.
- **Limits.** `previewRoots` carries the project's `check` limits from labshelf.yaml ([library-format.md](library-format.md#labshelfyaml)): `pageLimit`, `wordLimit` and `countUpTo` (`references` or `end`, `references` when absent). Each root carries `words`, the words of its sources up to the references heading or to the end, across `\include` and `\input`; the reader counts pages up to the same point. The reader asks the host to change the limits with `setCheckLimits` (`pages`, `words`: a positive whole number, or null to remove it; `countUpTo`); a field left out keeps its value. The host writes labshelf.yaml and answers with a new `previewRoots`.
- **Build options.** `previewRoots` carries `options`: `autoCompile` (the user's setting), `engine` for a LaTeX project, `null` while the project has not chosen one (absent for Typst, which has no engine choice) and `includeOnly` (`file`, the focused included file, and `on`) only when the shown root uses `\include`. The reader sends `setAutoCompile`, `setEngine` and `setIncludeOnly`; the host applies the change, rebuilds when it changes the output, and answers with a new `previewRoots`. With `includeOnly` on, the host builds only that file, and the other chapters keep their numbering.
- **Problems on the PDF.** Each root carries `pdfProblems`, one ordered list per build that next/previous problem walks: undefined citations, undefined references, overfull lines and cited preprints that have a published version. Each has its `kind`, the cite key or label it is about (`subject`), a message, its source `file` and `line` when known, and `area` when the host could place it on the PDF. Placed problems come first in reading order (page, top, left), the rest after in file and line order. LaTeX places them through SyncTeX; Typst places only citation problems, through the citations its last build placed. Each root also carries `cites`, the number of citations in its sources. The reader shows citation problems as underlines and overfull lines as margin marks.
- **Source lines.** The reader asks the host to open a source line with `openSourceLine` (`file` relative to the project folder, `line` from 1). The host opens only files inside the project folder; anything else is logged and ignored.
- **Project commands.** `runCommand` asks the host to run `compareVersions`, `markVersion` or `checkBeforeSubmitting` on the shown root's project. `previewRoots` carries `checks`, the number of findings of the last pre-submission check, absent before the first one.
- **Source and preview positions.** Points travel in PDF user space: page number and points from the page's top-left corner. Only a preview reader (`ReaderBootParams.preview`) reports a double-click, or the PDF-to-code action, as `showSource`; a library reader leaves double-clicks alone. The code-to-PDF action sends `revealCursor`, and the host answers with the editor cursor's point. The host reveals a point and the reader scrolls to it and marks it; a page number past the document's last page is clamped to it.
- **Review notes.** In a preview reader the selection bubble offers a comment; the note goes to the host as `addReviewComment` with `point` (the start of the selection, in the same PDF user space as `showSource`), `quote` (the selected text) and `note` (not blank). The host maps the point to a source line with SyncTeX and adds a comment thread there, on the quote when that line or one near it holds it; with no source line it tells the user and logs the point.
- **Citations.** A preview reader asks which cited papers stand behind a link, or behind text it reads as a citation, with `lookupCitation`: a request number, the place as a page area in the same space as points, whether it is a link, and the link's destination name when it has one. The host always answers with `citation` under the same number, also when it finds nothing or fails, so the reader never waits; each entry is a cite key with its library paper when the library has one. A paper carries its id, title, authors and optionally its year, reading status and quoted highlights (text and page); a reader shows only what the host sends. A paper may also carry its `venue` and its library `folder`, and each highlight its `color`. An entry may carry `bib` (title, authors, year, venue from the user's `.bib` when no library paper has the key), `site` (the `file`, `line` and command text of the citing `\cite`), `citedPage` (the page a `[p.~N]` supplement names, whose highlights the card shows first) and `fix`, the one fix the card offers: `replace` with a `suggestion` for an undefined key, `update` with the published `venue` for a preprint, or `add` for a key only the `.bib` has. The reader applies a fix with `fixCitation` (`replace` with `key`, `replacement`, `file`, `line`; `update` or `add` with `key`); the host edits the source, the `.bib` or the library and marks the root stale. `openCitedPaper` may name a `page` to open the paper at.
  - LaTeX: a destination named `cite.<key>` (hyperref; biblatex writes `cite.<n>@<key>`) names its key, and any other LaTeX link names none. Text without a link, from a build without hyperref, goes through SyncTeX to the keys cited on its source line.
  - Typst: a link names the citation that the last build placed inside it.
  - Hovering a single citation shows a card with the byline and year, the REF or BIB tag, the title, the venue and folder, the source line of the citing command, the highlights on the cited page followed by the rest folded, and Open at p. N or Go to source; several citations show one row per key. Clicking a citation link whose key has a library paper opens that paper (`openCitedPaper`) instead of jumping to the bibliography; any other link keeps its jump.
- **The browser preview runs in a frame of the library page.** Page and frame exchange `postMessage`; the frame forwards each preview request to the page, which serves Recompile, a problem's source line, Compare (opens the project's History tab), Mark version and the check limits, and logs every other request as a warning. Its roots carry `sourceLinks: false`, so the reader hides Comment in the selection bubble; the reader shows Comment only while the shown root has `sourceLinks`.

## Changes

A host can mark regions of the PDF as changed, e.g. what differs from another version of the paper ([library-format.md](library-format.md#labshelfversions)). It sends `showChanges` with page areas in the same space as preview points; the reader draws them over the pages and keeps them through zoom and re-rendering. Each message replaces the earlier marks, and an empty list clears them. A reload request drops the marks sent before it, because they describe the document they came with; marks sent after it apply to the reloaded document. Any reader accepts the message, library or preview.

## Host-specific constraints

| Host | Constraint |
|---|---|
| VS Code | strict webview CSP with a nonce; assets through `asWebviewUri`; default webview CSS and theme variables are injected by VS Code |
| Browser | MV3 forbids inline scripts; the manifest needs `'wasm-unsafe-eval'` for pdf.js; minimum versions are Chrome 125 and Firefox 128 (the pdf.js 6.3 floor); the reader page never loads the library page's `base.css` |
